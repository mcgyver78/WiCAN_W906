# WiCAN for the Mercedes-Benz Sprinter W906 (EU)

**English** | [Deutsch](W906.md)

This fork of [meatpiHQ/wican-fw](https://github.com/meatpiHQ/wican-fw) adds support for the
**Mercedes-Benz Sprinter W906 (NCV3, 2006–2018), European version**. Target hardware is the
**WiCAN OBD (V300, ESP32-C3)**.

> **Not for US vehicles.** Dodge/Freightliner/US Mercedes Sprinters use different engine control units, software and
> emission equipment. Profiles and PIDs from US sources (e.g. ScanGauge X-Gauges) do not match EU vehicles, and vice
> versa.

**Status:** tested on a W906 316 CDI (OM651, Delphi CRD3, model year 2016).

* Wake-up, 33 engine values every second via MQTT, idle mode with ignition off
* Read and clear trouble codes of 18 control units
* Node-RED dashboard (e.g. on Victron Venus OS)

Other engines (OM646, OM642) are not covered yet.

## The problem

1. **The diagnostic CAN at the OBD port is silent.** The diagnostic CAN (OBD pins 6/14, 500 kbit/s, 11 bit) sits
   behind the EZS gateway and only starts its traffic once a tester transmits.
2. **Standard PIDs don't work.** The engine ECU does not answer mode 01. The values are only available through
   manufacturer specific UDS services (`22 xxxx`).
3. In ELM327/AutoPID mode the WiCAN firmware could not send raw CAN frames, so it could not wake the bus.

## Installation

### 1. Firmware

* **Prebuilt:** download `wican-fw_obd_*.bin` from the [releases](https://github.com/mcgyver78/WiCAN_W906/releases).
  GitHub Actions also builds the firmware on every push with firmware changes
  ([Build Firmware (WiCAN OBD V300)](.github/workflows/build-firmware.yml), artifact `wican-fw-obd-v300`).
* **Build yourself:** install ESP-IDF v5.5.2, then `idf.py build`. The target `esp32c3` is already set in the
  `sdkconfig`. **Don't run `idf.py set-target`:** it replaces the `sdkconfig` with defaults (no Bluetooth, wrong
  partition table) and the build fails.

Flash it in the WiCAN web interface under *Firmware Update* (OTA). For flashing via USB follow
[docs/content/0.Config/4.Firmware-Update.md](docs/content/0.Config/4.Firmware-Update.md) (mind the boot pins).

### 2. Profile and AutoPID settings

The web interface only lists the profiles of meatpiHQ/wican-fw, so create an upload file (also attached to the
releases):

```bash
python3 tools/w906/make_car_data.py -o wican_w906_car_data.json
```

The file contains the profile **and** the AutoPID settings: *Vehicle Specific* on, all values every second, as one
JSON on the MQTT topic `wican/sprinter/engine`. `--topic` changes the topic, `--period` the interval in ms.

1. Under *Settings* choose **Protocol = AutoPID**, enable **MQTT** and enter the broker (e.g. Venus OS:
   `mqtt://<IP>`, port `1883`). Save.
2. Load the file via *Upload Configuration*. **Then click *Reboot* under *System*.** The web interface says
   "Rebooting…" but doesn't restart, and AutoPID only reads its settings at startup.
3. Recommended: under *Settings* set **Auto-Disable AP = enable**. The WiCAN turns off its own access point once it
   has an IP address in the vehicle WiFi. If that WiFi is unavailable, the access point comes back and the WiCAN
   stays reachable at `192.168.80.1`.

> **Important:** do **not** save the *Automate* page afterwards. The web interface doesn't know the W906 profile and
> replaces it with "Not Selected". To change something, create the file again and upload it.

The WiCAN then publishes every second:

```json
{"ENGINE_RPM":758.25,"COOLANT_TMP":47.5,"ENGINE_OIL_TEMP":46.5,"RAIL_PRESSURE":251,"BOOST_PRESSURE":1023.5, …}
```

### 3. Sleep and idle mode

**Sleep:** enable sleep under *Settings*. Recommendation: **12.5 V** and **16 min**. If the voltage stays below that
threshold for this time, the WiCAN switches off. As soon as it rises again (engine running, DC-DC charger, shore
power), the WiCAN restarts. Its voltage reading is 0.1–0.2 V off, no fine tuning needed.

**Idle mode (automatic):** after several unanswered requests in a row (ignition off) the WiCAN only sends **one
wake-up attempt every 30 s**, rotating through the control units. Instead of stale values it publishes
`{"ecu":"offline"}` every 10 s and reports the ECU as offline. After switching the ignition on, values return within
10–30 s. This keeps the diagnostic CAN quiet, even if a battery maintainer keeps the voltage above the sleep
threshold. Idle mode is part of the W906 upload file (`"idle_mode": "enable"`) and only applies while polling.

### 4. Node-RED dashboard (optional)

[tools/w906/node-red](tools/w906/node-red) contains two flows for Node-RED (e.g. Victron Venus OS).

* **Requirements:** the palette **`node-red-dashboard`**, and for the *Fehlerspeicher* page also
  **`node-red-node-ui-table`**. Install both **before importing** via *Menu → Manage palette → Install*. If one is
  missing, Node-RED starts no flow at all after the deploy, not even your other flows.
* **Import:** via *Menu → Import*, then *Deploy*.
* **Broker:** both flows include the same MQTT broker config node "Venus OS MQTT" for `localhost:1883`. If your broker
  runs elsewhere, import both files first and change the address in that node afterwards. If Node-RED asks about the
  existing node during the second import, don't replace it.

| File | Dashboard tab | Content |
|---|---|---|
| `sprinter-dashboard.json` | **Sprinter** | Gauges and values in the groups engine, fuel, charge air, exhaust, DPF/EGR; 60 min history charts; status "ECU aktiv / schläft (IGN aus)" |
| `dtc-dashboard.json` | **Fehlerspeicher** | Buttons *Lesen* (read) / *Löschen* (clear, with confirmation), progress, trouble code table with plain text and classification |

The dashboard texts are German. `make_flow.py` and `make_dtc_flow.py` regenerate the flows:

* `--topic`: AutoPID topic of the WiCAN
* `--broker-id`: use an existing broker config node
* `--texts`: your own trouble code texts
* `--device-id`: fixed WiCAN for the trouble code page (needed with several WiCANs on one broker)

## Firmware extension: wake-up frames (`ATWU…`)

The ELM327 emulator understands additional AT commands. They are not part of the ELM327 standard and go into the
`init` of a vehicle profile or can be sent from a terminal:

| Command | Meaning | Default |
|---|---|---|
| `ATWUA iii,dddd…` | Add a raw 11 bit wake-up frame (max. 4 frames) | – |
| `ATWUA wwxxyyzz,dddd…` | Add a raw 29 bit wake-up frame | – |
| `ATWUC` | Clear all wake-up frames | – |
| `ATWUD hh` | Delay after waking, `hh` hexadecimal × 10 ms (e.g. `0A` = 100 ms) | `32` (500 ms) |
| `ATWUI hh` | Wake again if no response for `hh` seconds, hexadecimal (e.g. `0A` = 10 s); `00` see below | `05` |
| `ATWUS` | Send wake-up frames now | – |

**Data bytes of `ATWUA`:** the firmware sends 0–8 data bytes exactly as given (DLC = number of bytes). It doesn't add
an ISO-TP PCI byte. For diagnostic requests include the PCI byte yourself and pad to 8 bytes, like `023E005555555555`
(PCI `02`, TesterPresent `3E 00`, padding `55`).

Behaviour once a wake-up frame is configured:

* **Until the first response** and after an idle period of `ATWUI` seconds the firmware sends the frames 10 ms apart
  before the request and waits `ATWUD`. With `ATWUI00` there is no wake-up after an idle period.
* **If a request gets no response**, it wakes the bus again and retries the request once.
* It wakes at most once per second.
* `ATZ` and `ATD` reset the wake-up configuration.

The W906 profile wakes the bus with a physical TesterPresent to the engine ECU:
`ATWUA7E0,023E005555555555;ATWUD32;ATWUI04;`

**Notes on individual values:**

* **`ECU_DISTANCE` (601F) is not the odometer reading.** The instrument cluster only sends the total distance as five
  digits (0…99,998 km); the 100,000s digit is computed by the engine ECU and, per Xentry, can "in rare cases be
  wrong". On this vehicle it is: `ECU_DISTANCE` reads 48,872 km while the real odometer is 348,872 km (the "3" is
  missing). So the value is only the five-digit part, not the odometer.
* **Soot load (`DPF_SOOT_MASS`, `DPF_SOOT_SIM`) is an ECU estimate** (from DPF differential pressure and a model), not
  a physical measurement. The WiCAN reports exactly what Xentry shows.

More identified values that are intentionally not in the profile:

| DID | Xentry name (translated) | Formula |
|---|---|---|

The measured soot load is in `604B`: `/128` gives the percentage (Xentry "DPF soot content", 40–41 % here), `/1600`
the measured mass in g (Xentry 3.2–3.3 g). Both are matched against the Xentry DPF page on the vehicle (measured
3.31 g, simulated 1.51 g). The model value (Xentry ~1.7 g) is not confirmed yet; two more DIDs, `6043` and `6135`,
also read ~40 %.

**Still open:**

* **Soot mass model value:** the matching DID is not confirmed yet (`609F` looked right in the capture but read 0 on
  the vehicle).

* **Low fuel pressure and fuel pump delivery rate:** probably `6170` (`/32` bar) and `6175` (`*0.5` %), not
  confirmed.

## Trouble codes

### Read and clear with the WiCAN

In AutoPID mode the firmware reads the trouble codes of all 18 control units on request, just like the Xentry quick
test. Engine polling pauses for about 30–40 s. Tested on the vehicle: all 18 control units answer without security
access, a read takes about 35 s. In the clear test an unplugged air mass sensor left four codes in the engine ECU.
The firmware cleared them and the control unit confirmed it (36 s).

Before every run the firmware asks the engine ECU for the engine speed:

* **No response** (ignition off): aborted with `ecu_offline`. Nothing is sent to the other control units.
* **Clearing** only below 50 rpm, otherwise aborted with `engine_running`.

> **Caution when clearing:** all control units with entries are cleared, including engine, transmission, ESP, SRS
> (airbag) and EZS. Freeze frame data and readiness values are lost. Read first and note the codes. Only with
> **ignition on, engine off, vehicle standing**. The firmware can't check whether the vehicle is standing.

MQTT commands on `wican/<device id>/cmd`. The id is part of the status topic `wican/<device id>/can/status`.

| Command | Effect |
|---|---|
| `{"cmd":"read_dtc"}` | Read the trouble codes of all control units |
| `{"cmd":"clear_dtc"}` | Read, clear control units with completely read entries, read again |

* **The firmware ignores retained commands.** Otherwise e.g. `clear_dtc` would run again after every restart.
* While a run is in progress, further commands are rejected with `busy`.

The result is published on `<AutoPID topic>/dtc`, e.g. `wican/sprinter/engine/dtc`. Only the final result is
*retained*:

```json
{"state":"running","action":"read","ecu":5,"total":18}
{"state":"done","action":"clear","duration_ms":31500,"dtc_count":1,
 "ecus":[{"name":"N3/28 Motorelektronik (CDID3)","id":"7E0","protocol":"UDS","status":"ok","cleared":true,
          "dtcs":[{"code":"P242F-FA","status":"68","active":false}]}, …]}
{"state":"error","action":"clear","reason":"engine_running"}
```

* **`status` per control unit:**
  - `ok`
  - `no_response`: no response
  - `nrc_XX`: negative response, e.g. `nrc_22` = conditions not correct, `nrc_33` = access denied
  - `pending_timeout`: only *response pending* (`7F xx 78`), the actual response didn't arrive in time
  - `incomplete`: incomplete response (missing or reordered CAN frames). Such control units are never cleared.
* **`cleared`** (only when clearing, only for control units with entries): the control unit confirmed the clear.
* **`dtcs_omitted`:** if the result doesn't fit into one MQTT message (5 KB), the codes of the control units with the
  most entries are left out and replaced by their number.
* **`reason` of `error`:** `ecu_offline`, `engine_running`, `engine_state_unknown` (engine speed not readable,
  nothing cleared), `busy`, `out_of_memory`.
* The final result has no timestamp, the WiCAN has no clock.
* Clearing is permanent. If the cause is still present, the trouble code comes back.

The dashboard page **Fehlerspeicher** shows per code:

* **Plain text (local):** from the function node *Klartexte (lokal)* in the flow. The table is empty in the repo.
  Everyone enters the texts their own diagnostic tool (e.g. Xentry) shows for their own vehicle. The key is the code
  as displayed (`"P242F-FA"`) or without the suffix (`"P242F"`).
* **Classification:** computed from the code alone.
  - Area from the letter (P/C/B/U).
  - Standard or manufacturer specific from the number range (SAE J2012).
  - Failure type from the byte after the dash (ISO 14229 / SAE J2012, e.g. `-64` = signal plausibility failure).
* **Status:** from the UDS status bits (*aktiv* = active, *gespeichert* = stored, *Warnleuchte* = warning lamp).
  KWP codes have no standardised status bits. Unconfirmed clears and control units without a complete response are
  listed with their own status.
* Without trouble codes the table lists all control units as *i.O.* (OK).

Also:

* **Target WiCAN:** the only WiCAN that is currently online. With several WiCANs on one broker create the flow with
  `--device-id`.
* **Confirmation:** names the target WiCAN and the preconditions before clearing.
* **No answer:** if there is no feedback for 60 s, the status shows "keine Antwort vom WiCAN" (no answer from the
  WiCAN).
* **Stored result:** after a restart of Node-RED or the broker the last result is shown as "gespeichertes Ergebnis,
  Zeitpunkt unbekannt" (stored result, time unknown).

Trouble code texts from manufacturer databases (e.g. Xentry/Vediamo) don't belong in the repo, they are protected by
copyright and database rights.

### Control units and services (from the Xentry quick test)

Xentry wraps every request in a diagnostic session, the firmware does the same:

* **UDS:** `10 03` → `19 02 <mask>` → `10 01`, clear with `14 FF FF FF`.
* **KWP2000:** `10 92` → `18 02 FF 00` → `10 81`, clear with `14 FF 00`.

The names were assigned by the request order of the quick test. The codes of engine, B162, radio and air conditioning
were also checked against the Xentry display.

* **UDS response** `59 02 <mask> [code high, mid, low, status] …`. The first two bits give P/C/B/U, e.g.
  `24 2F FA` → P242F-FA.
* **KWP response** `58 <count> [code high, low, status] …`.
* Many control units first answer `7F xx 78` (*response pending*). In the Xentry capture the actual response arrived
  at most 520 ms (ESP) after a read request and at most 200 ms (engine) after a clear request, well within the
  response time of the profile (`ATST96`, about 614 ms).
* For the ESP Xentry sends a security access (`27 13/14`) before reading. The firmware doesn't do that and the ESP
  still answers.

## Findings from the CAN captures

### Wake-up

* Without a tester the diagnostic CAN is silent. With a tester `001`, `200`, `208` (every 20 ms) and `2F3` (240 ms)
  are sent.
* After every idle period **a tester frame came first**. The cyclic traffic started 10–15 ms later, and the engine
  ECU answered 1 ms after the request. A single physical frame to `7E0` is enough.
* With ignition off the engine ECU doesn't answer anymore, not even to wake-up frames. The WiCAN does not keep the
  vehicle awake.

### Other addresses

| Request → response | Note |
|---|---|
| `7DF` → `7E8` / `5FF` | UDS functional, `22 F8xx` is answered |
| `7E4` → `7EC` | UDS, answers `22 F100` |
| `7E0` mode 01 | no response (PID `42` → NO DATA) |

## CAN capture and analysis

Goal: capture the requests of Xentry and match them to the values using a screen recording.

1. **Setup:** connect the WiCAN and the Xentry VCI in parallel with an OBD Y cable.
2. **WiCAN as sniffer:** back up the configuration, then *Protocol = slcan*, *CAN Mode = silent*, MQTT off. Capture
   via TCP port 3333 (SLCAN `C`, `S6`, `L`) or with SavvyCAN (*Protocol = savvyCAN*, listen-only). Restore the
   configuration afterwards.
3. **Recording:** screen recording of Xentry with a visible clock, about 1 minute per actual values page, with the
   engine running and some throttle blips.
4. **Analysis:**

```bash
python3 tools/w906/can_log_analyzer.py capture.log --gap 1.0 --series --profile skeleton.json
```

* **Summary:** all CAN ids with count and cycle time.
* **Wake-up candidates:** the first frames after every idle period, with a ready `ATWUA…` command.
* **Diagnostic exchanges:** all ISO-TP requests and responses (including multi frame) with service, DID/LID, NRC and
  the bytes that change between responses.
* **`--series`:** value ranges of all `21xx`/`22xxxx` responses over time.
* **`--profile`:** profile skeleton with all requests. Names and formulas are added by hand.

The clocks of the Xentry PC and the capture often differ by seconds to minutes. Determine the offset with a known
value such as the engine speed.

Supported formats: SavvyCAN GVRET CSV, `candump -l`, `candump` console output and SLCAN (so the TCP port 3333 stream
can be analysed directly). "try:" only suggests harmless tester frames as a wake-up.
