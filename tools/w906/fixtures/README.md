# Fixtures

Hand-written reference data shared by the firmware host tests and, later, by the display firmware tests.
They are the contract: a test compares its output byte for byte with these files, the files are never
generated by the code under test.

- `dtc_state_*.json`: the `dtc` object of `GET /api/state` in each phase (see `main/dtc_state.h`).
- `api_state_*.json`: complete answers of `GET /api/state` (see `API.md` and `main/dtc_api.h`); `api_state_example.json`
  is the example of `API.md`, word for word.
- `api_body_*.json`: the bodies of the answers to `POST /api/dtc`, one per status and reason.

## Built from the schema, not captured from a vehicle

The files below were written by hand from the formats in `W906.md` (section "Fehlerspeicher"), `API.md` and
`main/autopid.c`. No adapter and no vehicle was involved: the trouble codes, status bytes, durations and values are
invented and say nothing about a real Sprinter. Only the form is binding. Replace them by captured answers once the
hardware is there, and keep the invented ones apart from those.

`mock_wican.py` answers exactly these texts in the scenario named; `test_api_contract.py` compares them byte for byte
and checks the files themselves against the format, the control unit table of the firmware and the vehicle profile.

- `dtc_result_read_empty.json`: `GET /api/dtc/result` after a read without trouble codes (scenario `no_codes`).
- `dtc_result_read_codes.json`: after a read with two UDS control units and two KWP control units that have codes and
  one control unit that does not answer (scenario `codes`). UDS codes have `active`, KWP codes do not.
- `dtc_result_clear.json`: after the clear that follows this read. `cleared` stands only at the four control units
  that had codes: twice confirmed and empty, once confirmed with the code back at once, once not confirmed.
- `dtc_result_shortened.json`: a read with 165 codes that did not fit into an MQTT message (scenario `many_codes`).
  The two longest lists are empty and counted in `dtcs_omitted`; `dtc_count` still counts every code.
- `autopid_data_ignition_on.json`: `GET /autopid_data` with the ignition on and the engine off, the 35 values of
  `vehicle_profiles/mercedes/sprinter_w906_om651.json` in the order of the profile (scenario `codes`).
- `autopid_data_ignition_off.json`: the same with the ignition off, no value is valid (scenario `ignition_off`).
- `car_config_w906.json`: `GET /load_car_config` for the W906 profile, class and unit from
  `.vehicle_profiles/params.json`.
